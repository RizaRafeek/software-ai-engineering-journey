    Schema:
        It dictates what tables exist, what columns live inside them, what data types those columns accept, and how tables relate to one another. 
        Think of it as the strict type-definition file for your database structure


    Constraints:
        rules enforced by the database engne to guranterr data integrity(bad/contradctory data never get saved)

        Types:
            NOT NULL:
                column cannot be blank
            UNIQUE:
                No two rows in the column will have same values
            CHECK:
                ensure value meets a specific condition : eg: age>= 18
            DEFAULT:
                inserts a fallback value automatically if you dont provide one
            

    Datatypes:

    NULL:
        null is not zero
        if you perform any mathematical operation with null, the result will be null eg: NULL + 5 = NULL


    List v/s database
        List:
            -stored in RAM 
            -Lifetimee tied to application lifecycle
            -single threaded/ process limits
        Database:
            -stored in Disk
            -Permanent memory (survives crashes)
            -can handle multiple users at a time

        Acid guarantee:
            the process doesnt get lost midway in database as it might happen in lists
            the database either completes the entire transaction or goes back to the state before the transaction started
            so nothing is lost or added unexpectedly

        Multiserver:
            database is built for multi-user

        Searching and Scalability:
            -Lists : uses linear search : very slow and expensive
            -database : Indexing (B-Tree) : hashmap is not odered so we use this

        Why multiple tables instead of one:
            -avoid redundant values
            -ease of updation(eg: phone number)
            -ease of deletion, insertion


    Primary key:
        A primary key must be unique, immutable (never change), and always present (never NULL)
